----------------------------------------------------------------------
0. THE FIVE FACTS THAT DRIVE EVERY DECISION
----------------------------------------------------------------------

F-1  THE DATA IS SMALL. Full corpus ~30MB gzipped: 80,252 sessions /
     883,764 steps / 365,065 turns / 16 config changes / 2 tenants /
     56 days. It fits in memory; a single Python process computes every
     metric in seconds. => We do NOT need a queue, event bus, worker
     fleet, or database. Those are the 100x story (Section 21), not the
     build.

F-2  THE DELIVERABLE IS ONE JSON FILE + ONE SCREEN. score.py reads only
     loop-report.json and is 100% deterministic. => Engineering effort is
     ranked by "does it change the report or the screen." Everything else
     is optional.

F-3  RULE 1 IS DISQUALIFYING. An LLM must never compute a fact that is in
     the logs. => Every scored number is produced by a deterministic
     function. The LLM only reasons over already-computed evidence and
     judges meaning (calibrated). We enforce this structurally, not by
     convention (Section 10).

F-4  THE SEALED RUN MUST RUN UNATTENDED. Day 6, a different dataset,
     no hand-holding, or it scores as failed. => The scoring-critical
     pipeline is deterministic and LLM-FREE. It must produce a valid,
     scoring report even if the LLM is down. The agent enriches; it is
     never load-bearing for the report (Section 16).

F-5  NOTHING IS HARDCODED TO VARIANT A. The screen and the report are
     pure functions of the corpus. Practice numbers exist to test
     against; the sealed set differs in days/tenants/slices.

1. ARCHITECTURE AT A GLANCE (RIGHT-SIZED)
----------------------------------------------------------------------

Two layers, three deployables, one provided service.

  LAYER 1 — DETERMINISTIC BACKBONE (the thing that scores)
    corpus/*.jsonl.gz + catalog.json
        -> analyzer/  (pure Python, stdlib, no LLM)
        -> loop-report.json  (schema-valid, deterministic)
        -> score.py (wired into CI every commit)

  LAYER 2 — AGENTIC ENRICHMENT (the thing that demos)
    agent/orchestrator drives the loop, calls DETERMINISTIC TOOLS that
    wrap the backbone, adds JUDGED signals (calibrated), narrates, and
    runs ONE replay per fix. Nondeterminism touches prose/ordering only —
    never a scored number.

  SERVING
    api/ (FastAPI) reads the report, exposes it, records human decisions,
    proxies replay. web/ (React) renders purely from the report.

  DIAGRAM
    ┌────────────┐   reads    ┌──────────────────────────┐
    │  corpus/   │──────────► │ analyzer  (backbone, LLM- │
    │ catalog    │            │ free, deterministic)      │
    └────────────┘            └───────────┬──────────────┘
                                          │ emits
                                          ▼
                              ┌──────────────────────────┐
        ┌─────────────┐ tools │  loop-report.json         │
        │ agent layer │◄──────┤  (contract w/ schema)     │
        │ orchestrator│──────►│                           │
        │ judge/verify│ writes└───────────┬──────────────┘
        └──────┬──────┘ judged/            │ served by
               │ narrative/verify          ▼
         one replay/fix           ┌──────────────────┐   REST   ┌───────┐
               ▼                  │ api (FastAPI)     │◄────────►│ web   │
        replay/serve.py (given)   │ + decision writeback│        │ React │
                                  └──────────────────┘          └───────┘

The only mutable state in the whole system is the human decision. The
analyzer output is immutable and reproducible.

----------------------------------------------------------------------
2. TECH STACK & RATIONALE
----------------------------------------------------------------------

  Analyzer backbone .... Python 3.11, STDLIB ONLY (gzip, json, csv,
       statistics, dataclasses, hashlib). Rationale: the kit is
       zero-dependency; stdlib guarantees the sealed run has no install
       step and no version drift. 883K dict rows aggregate in seconds.
       Optional: polars ONLY if profiling shows we need it — behind a
       flag, never in the sealed-run default path.

  Schema validation .... jsonschema (dev/CI only). The analyzer does not
       depend on it at runtime; validation is a gate, not a need.

  Agent layer .......... Python. LLM via a provider-agnostic gateway with
       structured (JSON) outputs, prompt+judge versioning, timeouts,
       retries, and an OFFLINE fallback that returns templates. Model:
       latest Claude (Opus/Sonnet) for reasoning; a smaller/faster model
       for the judge is fine as long as it is versioned + calibrated.

  API .................. FastAPI + uvicorn. Thin. No ORM.

  Persistence .......... FILES, not a DB. report.json (immutable, from
       analyzer) + decisions.json (append-only, from the API). A finalize
       step merges decisions into the report for submission. SQLite is an
       option if we want queryability, but files are enough at this scale
       and keep the sealed run trivially reproducible.

  Frontend ............. React + Vite + TypeScript + Tailwind. Pure
       function of loop-report.json. No client-side computation of any
       scored number.

  Replay ............... the PROVIDED replay/serve.py (HTTP, local,
       budget 40). We write a thin client with budget accounting.

  Tooling .............. Makefile targets, one run_sealed.sh, ruff/black
       optional, pytest for tests.

WHY NOT the distributed stack from Approach.txt: at 30MB it adds risk and
consumes the days that decide the score. We keep that design as the
documented 100x path (Section 21). Senior call: minimize moving parts so
the sealed run cannot fail on infrastructure.

4. DATA LAYER — LOADING & THE IN-MEMORY MODEL
----------------------------------------------------------------------

INPUTS (from kit/):
  corpus/sessions.jsonl.gz    one row per conversation (grain: session)
  corpus/agent_steps.jsonl.gz one row per execution step (grain: step)
  corpus/turns.jsonl.gz       transcript text (grain: turn) — used sparingly
  corpus/config_timeline.csv  16 timestamped changes
  corpus/feedback.csv         sparse CSAT (~8.6% of sessions)
  labels/outcome_labels.jsonl 400 human resolved/by-design labels
  labels/rubric_scores.jsonl  96 human 1-5 quality scores
  catalog.json                THE SEMANTIC CONTRACT — plan over this
  manifest.json               variant, days, row counts, epoch

KEY FIELDS WE RELY ON (from catalog + observed rows):
  session: session_id, tenant, day, channel, intent, agent_id,
           agent_kind {v3_agent|v2_flow}, model, prompt_version,
           kb_version, turns, duration_s, cost_usd,
           session_end {resolved|handoff|abandoned}, handoff_by_design,
           milestones_reached[], milestones_total, quality_score,
           judge_version {v1|v2}, csat, custom_dims{customer_ref, segment}
  step:    session_id, step_seq, day, step_type {turn|llm_call|tool_call|
           kb_lookup|routing|guardrail|handoff}, agent_id, agent_kind,
           intent, tool_name, outcome {ok|error|timeout|max_iterations|
           blocked}, error_class, status_code, response_bytes,
           result_field_count, retry_count, kb_hit, kb_top_score,
           milestone, duration_ms, cost_usd, input_tokens, output_tokens
  config:  day, date, tenant('*'=all), kind {kb|tool|prompt|model|
           routing|judge}, target, from_value, to_value, note

IN-MEMORY MODEL (built once at startup):
  sessions: list[Session]                      (~80k)
  steps:    list[Step]                          (~884k)
  steps_by_session: dict[session_id -> list[Step]]   (the primary index)
  sessions_by_id:   dict[session_id -> Session]
  config:   list[ConfigChange] sorted by day
  labels_outcome, labels_rubric

  Memory footprint: well under 1GB. Loading: stream gzip line-by-line
  (as starter.py does), parse JSON, append. Build indices in one pass.
  Target: full load < 10s.

JOINS — USE ONLY WHAT THE CATALOG BLESSES:
  step.session_id -> session.session_id ............ SOUND (m:1)
  turn.(session_id,turn_index) -> step ............. SOUND (1:m)
  session.(tenant,day) -> config.(tenant,day) ...... SOUND_WITH_CARE
        *** config.tenant may be '*' (applies to ALL tenants). Equality
            join silently drops the judge-version change (day 28). Always
            match tenant == c.tenant OR c.tenant == '*'.
  step.tool_name -> config.target (kind='tool' only) SOUND_WITH_CARE
        *** filter kind='tool' or it fans out.
  quality_score across judge_version ............... UNSOUND. Never trend
        quality across the v1->v2 boundary; segment or re-score.

DETERMINISM RULES (so runs are byte-reproducible and match score.py
tolerances):
  · Sort every collection before iterating (by session_id, day, step_seq).
  · Round metrics consistently (4 dp for rates, 2 dp for money/turns).
  · No set iteration without sorting. No dict-order reliance pre-3.7 (we
    are on 3.11, but sort anyway for cross-run stability).
  · seed any sampling with a fixed value; the backbone does no sampling.

5. METRICS ENGINE — CAPABILITIES, COVERAGE, CALIBRATION
----------------------------------------------------------------------

We treat catalog.capabilities[] as a REGISTRY. Each metric we author
maps to a capability and emits a schema metrics[] entry with fidelity +
coverage + plan (source/filter/denominator) + optional calibration.

CANONICAL METRICS WE COMPUTE (all deterministic):
  containment_rate     session; coverage 1.0; resolved OR (handoff AND
                       handoff_by_design). [A01]
  resolution_rate      session; coverage 1.0. [core detector input]
  tool_failure_rate    step; coverage = v3 share (0.72/0.93); outcome !=
                       ok over tool_call steps, v2_flow EXCLUDED. [A04]
  cost_per_session     session; coverage = v3 share (cost on llm_call only).
  kb_fallthrough_rate  step; coverage = v3 share; kb_hit=false / low
                       kb_top_score.
  turns_to_resolve     session; coverage 1.0. [F3 detector input]
  quality_score        session; JUDGED; per judge_version; calibrated.
  milestone_reached_rate session; funnel/drop-off per catalog milestones.
  silent_tool_success  step; DERIVED (class derivable_not_declared):
                       status_code==200 AND (response_bytes==0 OR
                       result_field_count==0). We DERIVE AND DECLARE it —
                       the catalog says that is a legitimate answer, not a
                       gap. [F2 detector]

COVERAGE (the denominator trap, C1):
  coverage(tenant) for any tool/cost/kb metric = v3_agent sessions /
  all sessions, computed FROM DATA per tenant. Expected ~0.7205 (acme),
  ~0.9308 (northwind). score.py checks within +/-0.03. We emit
  coverage.value + coverage.basis + coverage.excluded=["agent_kind=v2_flow"].
  NEVER blend tenants into one figure. Metrics are authored PER TENANT
  where coverage differs (starter.py does exactly this).

CALIBRATION (for judged metrics):
  agreement between our judge and labels/rubric_scores.jsonl (n=96) and
  outcome vs labels/outcome_labels.jsonl (n=400). Compute agreement
  WITHIN a judge_version (rubric scores carry judge_version_at_label_time).
  HARD RULE: if agreement rounds to >= 0.995 we FLAG IT AS A BUG in
  system_notes and investigate — human labellers disagree ~7.5%, so 1.00
  is not a perfect judge. score.py penalizes a reported 1.00.

FIDELITY MAPPING (score.py fidelity traps):
  A04 tool failure -> "measured"  (we executed the call).
  A09 abandonment REASON -> "judged" / gap REQUIRES_NEW_JUDGE. Never
      "measured". session_end='abandoned' is measured; WHY is judged.

6. DETECTION ENGINE — DETERMINISTIC DETECTORS + LOOKALIKE GUARDS
----------------------------------------------------------------------

Detection runs over stratified cohorts, never the aggregate.

COHORT GRID: tenant x intent x agent_id x {week or day-window}. Also
tool cohorts (tenant x intent x tool_name) for tool faults.

BASELINE SELECTION (this is the crux of accuracy):
  1. HISTORICAL — if the cohort exists before the change window, compare
     during-window vs before-window (same cohort).
  2. PEER — if the cohort has NO before-period (new intent/product),
     compare vs peer cohorts of the same class on the same agent in the
     same window. (F1: premium_card_info is new on day 34 -> peer
     baseline = other question-answering intents on the agent.)
  3. STANDARD-RELATIVE — compare vs the deployment's own top-decile
     standard for that cohort/metric (Section 8). Needed when the outcome
     metric is flat but efficiency degrades. (F3.)
  The chosen baseline and WHY are written into impact.derivation. This is
  worth Decision-Quality points; it is not optional.

THE THREE REAL-FAULT DETECTORS (each returns a finding + evidence):

  D-KB (kb.gap)  [F1]
    Signal: a cohort (esp. new intent) where kb_hit=false dominates and
    kb_top_score sits low (observed band 0.11-0.38) while cohort
    resolution << peer/standard. Confirm no before-period -> peer
    baseline. Attribute to a kb config change at/just before onset.
    Emit: cohort {intent}, metric resolution_rate, is_regression=true.

  D-SILENT-TOOL (tool.contract_break)  [F2] *** the invisible one
    Signal: tool_failure_rate FLAT (outcome='ok'), BUT silent_tool_success
    rises on a tool (status 200 + response_bytes==0 / result_field_count
    ==0), followed by same-tool retry_count>0 within the session and an
    unresolved end. Cohort resolution for that intent drops. This is
    invisible to any error-rate metric — that invisibility IS the
    evidence. Attribute to a tool config change on the tool_name.
    Emit: cohort {intent, tool}, metric resolution_rate (+ derived
    silent_success), is_regression=true.

  D-STANDARD (prompt.regression)  [F3] *** the outcome-flat one
    Signal: for an agent cohort, turns_to_resolve and cost_per_session
    rise sharply vs the cohort's own standard while resolution_rate is
    FLAT. Threshold alerting on outcomes misses this entirely; only a
    standard-relative measure sees it. Attribute to a prompt config
    change on the agent_id.
    Emit: cohort {agent_id}, metric turns_to_resolve (or cost), is_
    regression=true. NOTE: for replay this maps to metric median_turns.

THE THREE LOOKALIKE GUARDS (each emits is_regression=FALSE +
not_a_regression_because + a diagnosis with the matching cause_class —
this is exactly what score.py rewards for specificity):

  G-MIX (traffic_mix)  [D1] *** Simpson's paradox guard
    Test: did the AGGREGATE move because the cohort MIX moved, while
    per-cohort rates are flat? If an intent's traffic SHARE spiked (e.g.
    branch_locator 0.13 -> 0.44) and every stratified cohort is flat/
    slightly worse, it is a mix shift, NOT a quality event — in EITHER
    direction (aggregate can rise). Emit is_regression=false, cause
    traffic_mix. GUARD: never flag on an aggregate movement without
    stratifying first.

  G-LOAD (load)  [D2]
    Test: volume spike (e.g. 4x) with p95 latency/timeouts up, but
    quality/resolution flat, and it SELF-CORRECTS inside the window. A
    platform reliability event, not a quality regression. Emit is_
    regression=false, cause load.

  G-JUDGE (judge_change)  [D3]
    Test: a judged-quality drop that coincides with a judge config change
    (day 28, tenant '*') and appears across BOTH tenants simultaneously.
    judge_version is stamped on every value -> refuse the cross-boundary
    comparison. Emit is_regression=false, cause judge_change. This is
    also Rule 2 in action: we never trend the yardstick.

DENOMINATOR TRAP GUARDS:
  · v2_flow: any tool/cost/kb metric excludes agent_kind='v2_flow' from
    the denominator and states coverage (Section 5).
  · customer_ref: any request to break a metric down by custom_dims.
    customer_ref is REFUSED with the cardinality budget (200) cited —
    a planner error, not a computation. gaps verdict CARDINALITY_REFUSED.

STRAY-FINDING DISCIPLINE (score.py penalizes findings matching neither a
fault nor a decoy): we only emit is_regression=true when a cohort clears
a significance + effect-size + attribution bar. Precision > recall:
"flagging one false regression costs more than missing a real problem."

----------------------------------------------------------------------
7. DIAGNOSIS & ATTRIBUTION ENGINE
----------------------------------------------------------------------

For each true finding, assign a cause_class (closed enum) and attribute a
config change.

cause_class enum: kb.gap, tool.contract_break, tool.outage,
  prompt.regression, model.change, routing.error, traffic_mix, load,
  judge_change, unknown.

ATTRIBUTION ALGORITHM:
  1. Find config changes for the finding's tenant (OR '*') within
     [onset-3, onset+3] days.
  2. Filter to changes whose KIND matches the fault signature:
       kb.gap -> kind 'kb'; tool.contract_break -> kind 'tool' on the
       cohort's tool_name; prompt.regression -> kind 'prompt' on the
       cohort's agent_id.
  3. Pick the nearest matching marker. Emit attributed_change {kind, day}.
     score.py awards +0.05 when kind matches and |day - onset| <= 2.

MISATTRIBUTION GUARD (a real trap in the data): nearby changes that are
NOT the cause must be rejected explicitly. E.g. F3's prompt change is
day 46, but there is a day-41 ROUTING change on the SAME agent
(acme_main_v3). The behaviour change tracks the prompt marker, not
routing; we record the rejected candidate in evidence. Same care: F1's
onset day 34 is a KB change (correct), but day-34 also sees normal KB
refreshes elsewhere — match on tenant+kind+cohort, not day alone.

confidence: a deterministic score from (effect size, marker proximity,
signal specificity). Shown on screen; not required by the scorer, but
feeds honesty.

----------------------------------------------------------------------
8. STANDARD MINING ("WHAT GOOD LOOKS LIKE")
----------------------------------------------------------------------

Task 02. Mine the deployment's own best conversations, deterministically.

  For each (tenant, intent/agent) cohort and each metric:
    best   = top-decile value (the standard)
    median = cohort median
    deficit = median - best (or best - median depending on metric sense)
  Only from cohorts with enough n. Emit standard[] {tenant, cohort,
  metric, best, median, deficit, exemplar_n, golden_set_version,
  derivation}.

The golden set (exemplar session_ids) is FROZEN once mined and versioned
(golden_set_version). Rule 2: we never change it to make results look
better. The golden set also feeds the replay golden-set guard (Section
11) and the F3 standard-relative detector (Section 6).

score.py awards 3.0 loop points for a non-empty standard.

----------------------------------------------------------------------
9. IMPACT ENGINE
----------------------------------------------------------------------

For every true finding, compute the impact block from the corpus (never
asserted). Fields per schema:

  conversations_affected  = |sessions in cohort ∩ window|
  share_of_traffic        = affected / tenant sessions in window
  downstream:
    would_have_resolved_at_baseline = affected * (baseline_res - obs_res)
    unplanned_handoffs = |cohort sessions ending handoff, handoff_by_
                          design != true|
    abandoned          = |cohort sessions ending abandoned|
    extra_turns        = (obs_turns - standard_turns) * affected  [F3]
  cost_usd  = sum(cost_usd over cohort) if derivable else null
              (null is an honest answer; cost covers v3 only)
  days_running = window length in days (to "now"/data end)
  derivation  = a sentence that lets a reader re-check EVERY number
                above AND names the baseline and why it was chosen.

Reference target (F1, from the shipped example — this is the quality bar
for the derivation string):
  "239 sessions matched the cohort over 11 days (4.2% of tenant traffic
   in the window). Observed resolution 0.314 vs a baseline of 0.816 (no
   before-period, so baseline = other Q&A intents on the same agent in
   the same window); 120 would-have-resolved did not; 149 unplanned
   handoffs; 15 abandoned; cost summed over cohort, v3 only."

audience (required for regressions) — derived from cause_class:
  kb.gap -> [agent_builder, business_owner]; tool.* -> [platform_owner];
  prompt.regression -> [agent_builder].
if_nothing_changes (required) — one sentence grounded in the numbers.

----------------------------------------------------------------------
10. THE AGENTIC LAYER — ORCHESTRATOR, TOOLS, RULE-1 ENFORCEMENT
----------------------------------------------------------------------

The agent makes the loop feel autonomous and drives the demo. It reasons;
the TOOLS compute. Rule 1 is enforced by construction: the LLM has NO
access to raw corpus rows — only to tool outputs (already-computed
facts). It cannot fabricate a number because it never sees the data to
guess from.

ORCHESTRATOR — a state machine (not free-form autonomy):
  LOAD -> COMPUTE_METRICS -> DETECT -> VALIDATE_LOOKALIKES ->
  DIAGNOSE -> MINE_STANDARD -> PRESCRIBE -> REPLAY -> VERIFY ->
  DECISION_PENDING -> RECORD -> WRITE_REPORT
  Lookalikes short-circuit at VALIDATE -> DISMISSED. Gaps handled by the
  measurability registry (Section 12).

TOOL INTERFACE (deterministic; each wraps analyzer functions; see
Appendix A for signatures):
  get_metric, get_cohort_metrics, compare_baseline, detect_change_points,
  get_config_changes, get_conversation, search_conversations,
  get_execution_steps, calculate_coverage, calculate_calibration,
  check_measurability, mine_standard, create_fix, request_replay,
  get_human_labels.

WHAT THE LLM MAY DO (meaning + orchestration only):
  · Decide which cohort to investigate next.
  · Classify a semantic question ("was the user satisfied", A06/A09/A10).
  · Draft the operator narrative over computed evidence (narrate.py).
  · Propose a fix TYPE from the closed enum + risk + ship-blocker.
  · Decide WHEN to spend a replay call (after diagnosis).
WHAT THE LLM MUST NOT DO (facts): compute any rate, count, coverage,
  cause_class-as-fact, attribution day, or replay number. Those come from
  tools. (See Approach-Product.txt Section 4 / the Rule-1 table.)

LLM GATEWAY (llm_gateway.py):
  · provider-agnostic; structured JSON outputs (schema-validated).
  · timeouts + bounded retries + circuit-breaker.
  · prompt_version + model_version stamped on every call and into the
    report's version fields.
  · OFFLINE FALLBACK: if the LLM is unavailable, narrate.py returns
    deterministic templates and the judge falls back to a documented
    heuristic (declared as stubbed in system_notes). The REPORT STILL
    SCORES. This is the F-4 guarantee.

DETERMINISM OF THE AGENTIC PATH: because scored fields come from tools,
two runs produce identical scored numbers even though prose may differ.
We set temperature low for structured calls and pin prompt versions.

----------------------------------------------------------------------
11. PRESCRIPTION, REPLAY & VERIFICATION
----------------------------------------------------------------------

PRESCRIPTION (prescribe.py): map cause_class -> change_type (closed enum)
and predict the delta from the analytics (NOT the LLM):
  kb.gap            -> kb.add (fallback kb.synonym)
  tool.contract_break -> tool.validate (fallback tool.fallback)
  prompt.regression -> prompt.edit (fallback revert)
Emit prescriptions[] {id, diagnosis_id, change_type, target,
  predicted_delta{metric, from, to}, decision{asking_approval_for,
  risk_if_diagnosis_wrong, would_not_ship_if}, autonomy_rung}.
predicted_delta.to comes from the standard/peer baseline (what "fixed"
should look like), so we can later score prediction vs observed.

REPLAY CLIENT (verify.py) — the contract (from replay/serve.py):
  POST /replay {team, tenant,
                change:{type, target, description},
                cohort:{intent, from_day, to_day},
                golden_set:[session_id,...]}
  -> {run_id "rp_xx…", metric, before, after, delta,
      verdict "improved|no_effect|regressed",
      golden_set:{replayed, regressed, pass}, runs_used, run_budget}

  RULES WE ENGINEER AROUND:
  · BUDGET = 40 total per team. We call replay ONCE per diagnosed fix.
    Maintain a persisted counter + a cache keyed by (tenant, change,
    cohort) so a re-run never re-spends. The endpoint punishes brute
    force ("diagnose, then verify — the budget is the point").
  · A fix only moves the metric if change.type is in the fault's accepted
    fix classes. So a NO-EFFECT verdict is a VALID result, recorded
    honestly, never retried in a search loop.
  · metric is median_turns for prompt faults, resolution_rate otherwise —
    our predicted_delta.metric must match, or the before/after won't line
    up on screen.
  · Pass the golden_set so the endpoint reports regressions to known-good
    work; surface golden_set.pass on the screen.

VERIFICATION -> report verifications[] {prescription_id, replay_run_id
  (MUST start "rp_" or score.py ignores it), metric, before, after,
  verdict, golden_set_pass, prediction_error = predicted_delta -
  observed_delta}.

SELF-ASSESSMENT (the return arrow): aggregate prediction_error and hit
rate per change_type into self_assessment {cycles, prescription_accuracy,
downweighted, notes}. score.py rewards cycles >= 3. We report the TRUE,
small number — never inflated (Approach-Product.txt R4).

----------------------------------------------------------------------
12. MEASURABILITY REGISTRY (THE GAPS / REFUSAL ENGINE)
----------------------------------------------------------------------

Refusal is deterministic, not "the LLM said I don't know." A registry
maps each ask (asks.md A01–A11) to a measurability verdict, derived from
catalog.capabilities[].class:

  canonical              -> ANSWER (emit a metric)
  derivable_not_declared -> DERIVE, DECLARE, ANSWER (e.g. silent_tool)
  requires_new_judge     -> gap REQUIRES_NEW_JUDGE (A09 abandonment
                            reason)
  NOT_MEASURABLE         -> gap NOT_MEASURABLE (A11 failover)
  cardinality over budget -> gap CARDINALITY_REFUSED (customer_ref)
  coverage below floor   -> gap COVERAGE_TOO_LOW

A11 (the closer) emits gaps[] exactly:
  {ask_id:"A11", verdict:"NOT_MEASURABLE",
   why:"no failover mechanism exists; no failover event is emitted",
   nearest_proxy:"llm_call.retry_count>0",
   why_the_proxy_misleads:"those are quality retries at a different
     temperature; reporting them reads as 0% failover = false good news",
   required_event:{name:"failover", grain:"step",
     fields:["from_target","to_target","reason","recovered"],
     owner:"conversation-runtime"}}

score.py awards 3.0 (verdict) + 1.5 (required_event.fields overlap) +
0.5 (nearest_proxy AND why_the_proxy_misleads). We emit all of it.

Required asks to cover: A01 (answer, containment), A04 (answer, measured),
A09 (gap/judged), A11 (gap/NOT_MEASURABLE). We also answer the easy
canonical ones for metric coverage points.

----------------------------------------------------------------------
13. REPORT BUILDER
----------------------------------------------------------------------

report.py assembles loop-report.json in schema order:
  team, corpus (= manifest.corpus_variant), generated_at, system_notes,
  metrics[], standard[], findings[], diagnoses[], prescriptions[],
  verifications[], gaps[], self_assessment{}.

Required (schema): team, corpus, metrics, findings, diagnoses, gaps.
Conditional (schema if/then): a finding with is_regression=true MUST have
impact, audience, if_nothing_changes — our builder asserts this before
writing and fails loudly if missing.

VALIDATION GATE: validate against schema/loop-report.schema.json
(jsonschema, draft-07) in CI and in run.py (--validate). Then run
score.py against ground_truth (variant A) and print the scorecard. A
build that doesn't validate does not ship.

IMMUTABILITY: run.py writes report.json deterministically. The API never
mutates it in place; decisions live in decisions.json and are merged at
"finalize" time (Section 14).

----------------------------------------------------------------------
14. API LAYER
----------------------------------------------------------------------

FastAPI, thin, file-backed. Endpoints:

  GET  /api/report                 -> report.json merged with decisions
  GET  /api/findings               -> findings[] (+ derived view fields)
  GET  /api/findings/{id}          -> one finding + linked diagnosis/
                                       prescription/verification
  POST /api/findings/{id}/decision -> body {verdict, reason, decided_by}
        writes prescriptions[].approval; appends to decisions.json
  POST /api/replay/{prescription_id} -> proxies verify.py (budget-guarded)
  GET  /api/metrics, /api/gaps, /api/standard, /api/self_assessment

DECISION WRITE-BACK (satisfies "human decision written into the report"):
  · POST decision -> append {finding_id, prescription_id, verdict,
    reason, decided_by, at} to decisions.json.
  · GET /api/report merges decisions into prescriptions[].approval.
  · A "finalize" make target bakes decisions into the submitted
    report.json. This keeps the analyzer output reproducible while still
    delivering a report that contains the human decision.

No auth needed for the hackathon (localhost). Do not expose LLM keys or
replay internals to the browser (keys stay server-side).

----------------------------------------------------------------------
16. SEALED-RUN RUNBOOK (F-4 — THE UNATTENDED GUARANTEE)
----------------------------------------------------------------------

ONE command produces the scored artifact, no LLM required:

  run_sealed.sh:
    python3 -m analyzer.run \
      --kit "$SEALED_KIT" \
      --team "our-team" \
      --out loop-report.json \
      --validate                # schema-validate before exit
    # (optional, only if LLM is up) agentic enrichment + replay:
    python3 -m agent.orchestrator --report loop-report.json \
      --replay-url "$REPLAY_URL" || echo "enrichment skipped (backbone
      report already valid and scoring)"

GUARANTEES:
  · The backbone (analyzer.run) has ZERO network/LLM dependency. If the
    room network, the LLM, or the replay endpoint is down, we still emit
    a valid, scoring report.
  · The agentic step is best-effort and idempotent; failure degrades to
    the backbone report, logged in system_notes as "enrichment skipped".
  · No interactive prompts. No manual edits. Exit non-zero only on a
    schema failure (which CI has already prevented).
  · The replay endpoint on Day 6 is organiser-hosted (0.0.0.0); we point
    --replay-url at it. Budget accounting persists across attempts.

FAILURE MODES HANDLED: partial/corrupt lines (skip + count), missing
optional files (feedback/labels -> degrade coverage/calibration, declare
it), unexpected new tenants/intents (the pipeline is data-driven, so new
slices just flow through), replay budget exhausted (stop, report what we
have).

18. PERFORMANCE & DETERMINISM BUDGET
----------------------------------------------------------------------

  Load full corpus ............ < 10 s (stream + index)
  Compute all metrics ......... < 5 s
  Detect + diagnose + impact .. < 5 s
  Report assemble + validate .. < 1 s
  Total backbone .............. < 25 s single process, < 1 GB RAM
  Agentic enrichment .......... bounded by LLM latency; not on the
                                critical scoring path.
  Replay ...................... 1 call per fix, <= 3 fixes => <= a few
                                calls of the 40 budget.
If we ever exceed memory/time (we won't at this scale), the escape hatch
is per-tenant streaming — already the 100x partitioning boundary.

19. OBSERVABILITY & SECURITY (RIGHT-SIZED)
----------------------------------------------------------------------

OBSERVABILITY: structured logs from the orchestrator (state transitions,
tool calls, LLM prompt/model versions, replay budget). A small
"run manifest" in system_notes: rows read, coverage per tenant, LLM
used yes/no, replay calls used. This doubles as demo material and as the
self-monitoring story.

SECURITY (hackathon-appropriate): LLM/API keys via env/secrets, never in
the browser or the report. Replay URL server-side. No PII leaves the box;
custom_dims.customer_ref is never rendered or grouped (cardinality
refusal). Treat all corpus text as data, never as instructions to the
LLM (prompt-injection hygiene in the judge/narrator).

----------------------------------------------------------------------
20. VERSIONING (RULE 2 — NEVER CHANGE THE YARDSTICK)
----------------------------------------------------------------------

Stamp and freeze:
  metric_definitions_version, judge_version (v1/v2 as in data),
  golden_set_version, detector_version, prompt_version, model_version,
  dataset_version (manifest.corpus_variant).
We may change the AGENT (propose fixes). We NEVER change metric
definitions, judge versions, or the reviewed good set to improve apparent
results. Any judge change is treated as data (D3), not as a tuning knob.

----------------------------------------------------------------------
21. THE 100x SCALING STORY (WHERE APPROACH.txt'S DESIGN LIVES)
----------------------------------------------------------------------

We BUILD the single-process analyzer; we PRESENT the distributed design
as the honest answer to "what breaks at 100x":

  · Ingestion: corpus streamed from object storage; partitioned by
    (tenant, day). Analyzer becomes a map over partitions.
  · Compute: horizontally-scaled stateless workers on a job queue; each
    owns a partition; results reduced to cohort metrics in a columnar
    analytical store for fast slice queries.
  · State: findings/decisions move from files to Postgres; reports to
    object storage.
  · Orchestration: the state machine becomes an event-driven workflow
    (DETECTION_DONE -> DIAGNOSE ...), with idempotency keys
    (run:finding:stage) and retries/dead-letter for unattended runs.
  · Replay at scale: a rate-limited internal service with caching by
    (cohort, change) so we never re-probe a hypothesis.
  · The PRODUCT surface and the report CONTRACT are unchanged — only the
    substrate scales. That is why the same screens rendered the sealed
    run unattended today.

This reframes the earlier architecture as an asset (foresight) instead of
a liability (over-build).

----------------------------------------------------------------------
22. TECHNICAL RISK REGISTER
----------------------------------------------------------------------

  TR1 LLM in the scoring path -> sealed run fails if LLM is down.
      MIT: backbone is LLM-free and always emits a scoring report (F-4).
  TR2 Rule-1 violation creeps in (LLM computing a fact).
      MIT: LLM has no raw-data access; only tool outputs. Code review the
      tool boundary. (Breaking Rule 1 is disqualifying.)
  TR3 Nondeterminism -> report changes between runs / fails golden test.
      MIT: sort everything, fixed rounding, low-temp structured calls,
      snapshot tests.
  TR4 Coverage/denominator wrong (v2_flow counted) -> honesty points lost
      and metrics misleading.
      MIT: coverage computed per tenant from data; asserted ~0.72/0.93 in
      tests (score.py tol 0.03).
  TR5 False alarm on a lookalike -> heavy specificity penalty.
      MIT: stratify before flagging; the three guards; precision bar on
      every true finding; stray-finding check.
  TR6 Replay budget burned by probing.
      MIT: one call per diagnosed fix; persisted counter + cache; no
      search loops.
  TR7 Calibration reported as 1.00 -> flagged as a bug by score.py.
      MIT: compute honestly against labels; if ~1.00, investigate + note.
  TR8 Frontend renders a number not in the report -> loses traceability.
      MIT: UI is a pure function of the report; no client-side math;
      review for orphan figures.
  TR9 Misattribution to a nearby config change (F3 routing vs prompt).
      MIT: match tenant+kind+cohort, nearest marker, record rejected
      candidates.
  TR10 Hardcoding variant-A specifics -> sealed run shows wrong data.
      MIT: data-driven throughout; test against example reports + sample.

APPENDIX A — DETERMINISTIC TOOL CONTRACTS (agent/tools.py)
----------------------------------------------------------------------

All return already-computed FACTS. The LLM never sees raw rows.

  get_metric(metric_id, tenant?, cohort?, window?)
      -> {value, numerator, denominator, fidelity, coverage{value,basis,
          excluded}, calibration?}
  get_cohort_metrics(tenant, dims:[intent|agent_id|tool_name|week],
                     metric, window?)
      -> [{cohort, value, n}]           # stratified, never aggregate-only
  compare_baseline(tenant, cohort, metric, window)
      -> {observed, baseline, baseline_kind:[historical|peer|standard],
          baseline_why, delta}
  detect_change_points(series)          -> [{day, magnitude}]
  get_config_changes(tenant, day_range) -> [{day,kind,target,from,to,note}]
                                           # includes tenant=='*'
  get_conversation(session_id)          -> session + steps (read-only)
  search_conversations(filter)          -> [session_id,...]  # bounded
  get_execution_steps(session_id)       -> [step,...]
  calculate_coverage(tenant, metric)    -> {value, basis, excluded}
  calculate_calibration(metric, judge_version)
      -> {agreement, n, judge_version}  # never asserts 1.0 silently
  check_measurability(ask_id)
      -> {verdict, why, nearest_proxy?, why_the_proxy_misleads?,
          required_event?}              # from the capability registry
  mine_standard(tenant, cohort, metric) -> {best, median, deficit,
                                            exemplar_n, golden_set_version}
  create_fix(diagnosis_id)              -> {change_type, target,
                                            predicted_delta}  # enum-bounded
  request_replay(tenant, change, cohort, golden_set)
      -> replay response (budget-accounted; cached by (tenant,change,cohort))
  get_human_labels(kind)                -> labels for calibration

APPENDIX B — ENUMS & MAPPINGS (single source of truth)
----------------------------------------------------------------------
  cause_class: kb.gap | tool.contract_break | tool.outage |
    prompt.regression | model.change | routing.error | traffic_mix |
    load | judge_change | unknown
  change_type: kb.add | kb.synonym | prompt.edit | tool.validate |
    tool.fallback | routing.change | revert | no_action
  gap verdict: NOT_MEASURABLE | REQUIRES_NEW_JUDGE | COVERAGE_TOO_LOW |
    CARDINALITY_REFUSED
  audience: business_owner | agent_builder | platform_owner

  cause_class -> change_type (prescription):
    kb.gap -> kb.add (fallback kb.synonym)
    tool.contract_break -> tool.validate (fallback tool.fallback)
    prompt.regression -> prompt.edit (fallback revert)
  cause_class -> audience:
    kb.gap -> [agent_builder, business_owner]
    tool.* -> [platform_owner]
    prompt.regression -> [agent_builder]
  replay metric by cause: prompt.* -> median_turns; else resolution_rate.

APPENDIX C — SCORING HOOKS (WHAT THE REPORT MUST CONTAIN)
----------------------------------------------------------------------
  Accuracy (20): per fault, a finding whose cohort key matches (intent/
    tool/agent_id), window overlaps onset (detect within ~10 days), a
    linked diagnosis with the right cause_class, and attributed_change
    {kind, day within +/-2}.
  Specificity (15): for each decoy, a finding is_regression=false WITH
    not_a_regression_because AND a linked diagnosis whose cause_class is
    traffic_mix / load / judge_change. No stray true findings.
  Honesty (12): every metric has fidelity + coverage; tool metrics'
    coverage within 0.03 of 0.72/0.93; a judged metric has calibration
    < 0.995; A11 gap NOT_MEASURABLE with required_event.fields +
    nearest_proxy + why_the_proxy_misleads; A04 measured, A09 judged.
  Loop (8): standard non-empty; diagnoses linked to findings;
    prescriptions linked to diagnoses with predicted_delta; verifications
    with replay_run_id starting "rp_"; self_assessment with cycles >= 3.
