====================================================================== 1.
CHALLENGE IDENTITY
======================================================================

Challenge: Nexus Loop

Subtitle: Building an Autonomous Improvement Loop for AI Agent
Deployments

Organization: Yellow.ai

Core loop: Detect -> Diagnose -> Prescribe -> Verify

Team requirements: - Minimum 1 second-year student - Minimum 1
first-year student - Team size: 7 per team

======================================================================
2. PROBLEM OVERVIEW
======================================================================

Scenario: A bank operates an AI agent on WhatsApp. The agent: - Talks to
customers. - Answers questions. - Calls the bank’s own APIs. - Reads a
knowledge base. - Hands over to a human when stuck. - Logs all of these
actions.

Current industry problem: - Millions of conversations run every day
across hundreds of companies. - When something breaks, people often
learn about it from a customer complaint. - Humans then guess what
changed. - They manually inspect transcripts. - They edit prompts. -
They hope the fix worked. - Nothing systematically verifies whether the
fix actually worked.

Challenge objective: Build the system that reads the existing agent logs
and closes this improvement loop.

The system should: 1. Find what broke. 2. Explain why it broke. 3.
Identify who must act. 4. Quantify what it costs if nobody acts. 5.
Propose a fix when possible. 6. Test/prove whether the fix works. 7. Put
the final decision in human hands. 8. Record that human decision.

One-sentence task: From eight weeks of logs from an AI agent deployment
that the team has never seen before, produce: - One report file
explaining what broke, why, who must act, and what could not be
measured. - One screen a human can read and act from.

Product balance: - Engineering half - Product half

5. PLANTED DATASET PROBLEMS
======================================================================

The practice data contains deliberately planted problems. The practice
dataset includes an answer key for self-checking.

  -------------------------
  5.1 THREE REAL PROBLEMS
  -------------------------

REAL PROBLEM A: - A new product launches. - There is nothing about the
product in the knowledge base.

REAL PROBLEM B: - An API starts returning empty results. - The API still
reports success.

REAL PROBLEM C: - A prompt change makes conversations approximately
twice as long. - Outcomes do not change.

Expected behavior for every real problem: - Find the problem. - Name the
affected traffic slice. - Quantify the impact. - Identify the cause. -
Point to the responsible configuration change where applicable.

Additional challenge properties: - One real problem has no “before”
period. Its baseline must be peer traffic. - One real problem is
invisible in the obvious error-rate metric. - One real problem does not
move the outcome metric at all.

  -------------------------------------
  5.2 THREE LOOKALIKES / FALSE ALARMS
  -------------------------------------

LOOKALIKE A: - A marketing campaign changes the mix of questions users
ask.

LOOKALIKE B: - A flash sale causes traffic and latency to spike for four
days.

LOOKALIKE C: - The quality-scoring rubric changes version halfway
through.

Required behavior: - Examine each lookalike. - Explicitly dismiss each
as a non-problem in writing. - Do NOT incorrectly flag a lookalike as a
regression.

Key principle: Flagging one false regression costs more than missing a
real problem.

  -------------------------------
  5.3 ONE UNANSWERABLE QUESTION
  -------------------------------

Question: “What is our failover rate?”

Why it is unanswerable: - The runtime has no failover mechanism. -
Therefore, no failover event is ever logged.

Required response: - Refuse to provide a failover rate. - Specify the
exact event that would need to exist in the data to answer it.

  ---------------------------
  5.4 TWO DENOMINATOR TRAPS
  ---------------------------

TRAP A: - Legacy traffic logs contain no tool calls at all.

TRAP B: - One field is nearly unique per customer.

Required behavior: - State the true coverage of any tool-related
metric. - Refuse invalid breakdowns. - Cite the data/coverage
limitation.

6. LEVELS OF COMPLETION
======================================================================

The challenge defines three completion levels.

LEVEL 0 / START: Action: - Run starter.py. Result: - Two metrics. -
Honest coverage. - Valid report file. Machine score: 9.8 / 55

LEVEL 1 — TARGET BY DAY 3: Accomplishments: - Find one real problem. -
Quantify it. - Explain it. - Dismiss all three lookalikes. - Refuse the
unanswerable question. Machine score: 38.0 / 55

LEVEL 2: Accomplishments: - Mine what “good” looks like from the
deployment’s own best conversations. - Propose one fix. - Prove it on
the replay service. Machine score: 41.5 / 55

LEVEL 3: Accomplishments: - Find the other real problems. - Record a
human decision on each fix. - Keep a record of the system’s own hit
rate. Machine score: 46.3 / 55

Important scoring insight: - These are measured scores, not estimates. -
A Level 1 system with an excellent screen and decision layer can score
approximately 70/100. - A Level 3 system with neither can score
approximately 58/100. - Depth on one problem is better than breadth
across all eight report sections.

======================================================================
7. WHAT A “FINDING” MUST CONTAIN
======================================================================

A finding is a decision, not merely a number.

Every real problem reported must contain:

1.  Affected volume:
    -   Number of conversations affected.
    -   Share of total traffic affected.
2.  User impact:
    -   What happened to affected users.
    -   How many would have resolved but did not.
    -   How many reached a human who was not supposed to be involved.
3.  Duration:
    -   How long the problem has been running.
4.  Cost:
    -   What the problem has cost.
5.  Owner: Identify who needs to act:
    -   Agent builder.
    -   Business owner.
    -   Platform team.
6.  Consequence of inaction:
    -   One plain-language sentence explaining what happens if nobody
        acts.
7.  Calculation / derivation:
    -   Explain how every number was computed.
    -   Name the baseline.
    -   Explain why that baseline was selected.
    -   Make the derivation checkable against the same data.

Baseline requirements: - If a problem has no before-period, compare
against peer traffic. - If a problem looks identical to peers, use its
own historical past where appropriate.

8.  Evidence:
    -   Every figure must be computed from the data.
    -   Do not make unsupported assertions.

======================================================================
8. FIX PROPOSAL REQUIREMENTS
======================================================================

If a fix is proposed, frame it as a decision.

The proposal must state: - What the human is being asked to approve. -
Risk if the diagnosis is wrong. - What condition would prevent the fix
from being shipped.

Human decision: - Screen must contain APPROVE / REJECT. - Human decision
must be recorded. - A rejection with a good reason scores as well as an
approval.

======================================================================
9. TWO NON-NEGOTIABLE RULES
======================================================================

RULE 1 — DO NOT ASK AN LLM WHAT THE LOGS ALREADY RECORD

Facts already available in logs must be computed directly.

Examples of facts that must NOT be delegated to a language model: -
Whether an API returned an error. - Which model served a turn. - Whether
a handoff happened.

Use a model only for questions of meaning, such as: - Was the user
satisfied? - Was the answer correct? - What was this conversation about?

If an LLM judge is used: - Version the judge. - Publish how often it
agrees with human labels in the kit.

Breaking Rule 1 is disqualifying.

RULE 2 — NEVER CHANGE THE YARDSTICK

The system may propose changes to the agent. It must NEVER modify the
evaluation yardstick.

The following are fixed: - Metric definitions. - Judge versions. -
Reviewed set of good conversations.

Disqualifying behavior: - Changing a metric definition to make the
result look better.

======================================================================
10. HONESTY FIELDS FOR EVERY METRIC
======================================================================

Every reported number must carry three honesty dimensions.

FIDELITY: How was the number obtained? Allowed concepts: - Measured
directly from logs. - Judged by a model. - Derived from other numbers.

COVERAGE: What share of traffic can actually produce this number?

CALIBRATION: For model-judged numbers: - How well does the judge agree
with human labels?

Important calibration fact: - Human labellers disagree with each other
approximately 7.5% of the time. - Therefore, a model judge calibration
of exactly 1.00 should be treated as a bug, not as evidence of a perfect
judge.

11. TASK BREAKDOWN
======================================================================

TASK 01 — DETECTION & DIAGNOSIS Input: Eight weeks of AI-agent
deployment logs.

    Must:
        - Find real problems.
        - Identify affected traffic slices.
        - Quantify impact.
        - Identify cause.
        - Identify responsible configuration change where applicable.
        - Examine lookalikes.

    Deliverable:

TASK 02 — STANDARD & FIX PROPOSAL Goal: Mine what “good” looks like for
the deployment from its own best conversations.

    Use the standard to:
        - Understand expected deployment behavior.
        - Identify deviations.
        - Propose a fix for a real problem.
        - State diagnosis risk.
        - Define what would prevent shipment.

    Deliverable:
        Proposed fix represented in the report and shown through the screen

TASK 03 — FIX VERIFICATION Goal: Test a proposed fix using the replay
service.

    Requirements:
        - Test on the affected cohort.
        - Compare before vs after.
        - A fix that has no effect is a valid result, not an error.

    Deliverable:
        Evidence showing whether the proposed fix actually worked.

TASK 04 — DECISION LAYER & SELF-ASSESSMENT Goal: Complete the
improvement loop.

    Requirements:
        - Record human decision for every proposed fix.
        - At highest level, maintain the system's own hit rate.

    Deliverable:
        - Human decisions.
        - Approve/reject outcome.
        - System self-assessment where applicable.

======================================================================

The report contains eight sections representing the improvement loop.

REQUIRED SECTIONS: 1. Metrics 2. Findings 3. Diagnoses 4. Gaps

OPTIONAL SECTIONS: 5. Standard 6. Prescriptions 7. Verifications 8. Self

SECTION 1 — METRICS Include: - What was measured. - Fidelity. -

22. CORE PRODUCT PRINCIPLES
======================================================================

The system is NOT simply an anomaly detector.

The complete improvement loop is:

    DETECT
        Find real problems in deployment behavior.

    DIAGNOSE
        Explain why the problem happened and identify the responsible
        configuration change where applicable.

    PRESCRIBE
        Propose an actionable fix, identify owner, risk, and consequences.

    VERIFY
        Replay the fix on the affected cohort and compare before/after.

    HUMAN DECISION
        Put final approval/rejection in human hands.

    RECORD
        Persist the human decision and, at the highest level, the system's
        own hit rate.

The system should: - Find real problems. - Avoid false alarms. -
Quantify impact honestly. - Explain causes. - Identify who needs to
act. - Explain consequences of inaction. - Refuse questions that cannot
be answered from available data. - Propose fixes. - Validate fixes. -
Keep humans in control. - Record human decisions.

24. HIGH-PRIORITY FAILURE MODES TO AVOID
======================================================================

FAILURE MODE 1: Reporting an anomaly without determining whether it is a
real problem.

FAILURE MODE 2: Flagging any of the three lookalikes as regressions.

FAILURE MODE 3: Using error rate alone and missing the problem that is
invisible in the obvious error-rate metric.

FAILURE MODE 4: Assuming every problem must have a before-period.

FAILURE MODE 5: Claiming a problem because a metric changed when the
outcome did not.

FAILURE MODE 6: Asking an LLM to determine facts already present in
logs.

FAILURE MODE 7: Reporting metrics without fidelity and coverage.

FAILURE MODE 8: Giving an answer to the failover-rate question even
though failover events are not logged.

FAILURE MODE 9: Using invalid denominators for tool-call metrics or
customer-level breakdowns.

FAILURE MODE 10: Changing the metric definition, judge version, or
reviewed good set to make results look better.

FAILURE MODE 11: Producing a beautiful UI with no real analytical
evidence.

FAILURE MODE 12: Producing a technically deep report that an operator
cannot act on.

FAILURE MODE 13: Proposing a fix without replay verification.

FAILURE MODE 14: Failing to record the human approval/rejection
decision.

FAILURE MODE 15: Requiring manual hand-holding during the sealed run.

======================================================================
25. FINAL SUCCESS DEFINITION
======================================================================

A successful Nexus Loop system is an autonomous, evidence-driven
improvement loop for AI-agent deployments.

It starts with: Agent logs.

It produces: Detect -> Diagnose -> Prescribe -> Verify.

It must additionally provide: - Honest measurement. - Explicit
uncertainty/gaps. - Actionable ownership. - Impact and cost of
inaction. - Human approval/rejection. - Recorded decisions. -
Self-assessment at the highest level.

The central product idea: An agent deployment records almost everything
it does, but the improvement loop is closed by a human moving between
multiple tools.

The challenge is to BUILD THAT LOOP.
